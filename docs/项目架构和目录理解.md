下面按“当前代码真实状态”总结，不把规划里还没落地的东西说成已完成。

  整体架构
  这个项目现在是一个基于 Claude Agent SDK 思路重构的代码审查系统。核心分层是：

  入口/启动层 -> orchestration 主编排 -> main agent loop -> skill -> subagent -> tool facade -> tool provider -> 产
  物

  关键依赖方向是：

  main / smoke
    -> bootstrap_runtime
    -> run_review
    -> MainAgentRuntime
    -> skill tools
    -> skills/*
    -> ToolFacade.tools_for(agent)
    -> ToolProvider(gitlab/infcode)

  主 agent 不直接读文件、不直接 grep、不直接调 git。工具能力必须通过 skill 内部的 ToolFacade 获取。

  目录结构
  RUN.sh
  项目启动脚本。当前调用的是 python -m cr_agent.main，而 main.py 目前只做 bootstrap ready，不跑完整 agentic 审查。

  INSTALL.sh
  安装/环境准备脚本。

  requirements.txt
  Python 依赖。

  config/
  静态策略配置，不是单次任务输入。

  - agent_tools.toml：配置不同 agent 能使用哪些工具。当前 context / dimension 是 *，summary 无工具。
  - dimensions.toml：维度列表和并发数。gitlab 10 个维度，infcode 为空时走 fallback。
  - config.toml、router.config.json：项目级配置样例/路由配置。

  cr_agent/
  核心 Python 包。

  cr_agent/main.py
  默认 CLI 入口。当前只执行 bootstrap_runtime，写 bootstrap_ready 结果。它不是完整审查入口。

  cr_agent/smoke.py
  当前真实 agentic review 冒烟入口。它会：

  1. bootstrap
  2. build main agent runtime
  3. 调 run_review
  4. 写最终结果

  cr_agent/bootstrap.py
  运行时装配层。负责：

  - 读取 agent_config.toml
  - 读取 context.json
  - 确定 platform
  - 解析 git token
  - 构建 CRG lifecycle
  - 构建 ToolFacade
  - 构建 summary/context/dimension runtime
  - 返回 RuntimeContext

  cr_agent/core/
  主流程、状态、契约、runtime 适配。

  - orchestrator.py：审查总编排，调用主 agent runtime，最后写 result.json / cr_result.md / run.log。
  - main_agent.py：把 skill 包装成主 agent 可调用工具，并实现主 agent SDK loop 适配。
  - sdk_runtime.py：Claude Agent SDK / LiteLLM Gateway 的 subagent runtime 适配。
  - agent_config.py：agent_config.toml Pydantic 配置模型。
  - review_input.py：context.json 输入模型。
  - review_output.py：最终 result.json 输出模型。
  - state.py：一次审查运行的状态，包括 attempt、tokens、errors。
  - usage.py：token usage 提取和累加。
  - artifacts.py：写结果文件。
  - errors.py：标准 runtime 错误类型。

  cr_agent/skills/
  四个审查阶段。

  - summarize/：启动 summary subagent 生成最终报告，目前 prompt 仍很简化。
  - validate_json/：纯代码校验最终报告结构，不调用模型、不拿工具。
  - registry.py：把四个 skill 注册给主编排使用。

  cr_agent/tools/
  工具抽象层。

  - provider.py：ToolSpec、统一工具返回结构 {ok,data,warnings,error}。
  - facade.py：按 agent allowlist 返回工具。
  - allowlist.py：读取 config/agent_tools.toml。
  - catalog.py：工具名注册表。
  - spec_sdk.py：把 ToolSpec 转成 Claude SDK MCP tool。
  - cr_native/：gitlab 平台本地工具 provider，包括文件、grep、git、CRG 生命周期等。
  - infcode/：infcode provider stub，目前主要是兼容扩展点。

  cr_agent/schemas/
  输入输出契约说明/JSON schema。

  cr_agent/agents/
  agent 定义/提示相关目录，目前不是主流程核心。

  prompt/
  审查 prompt。

  - business.md、security.md 等：维度 prompt。
  - summary.md：总结 prompt。
  - rules/：各维度评分规则。
    注意：当前 dimension_review 代码要求 subagent 返回 JSON，但部分维度 prompt 仍要求 YAML，这是后续要修的协议不一
    致。

  docs/
  项目文档、升级说明。

  tests/
  pytest 测试，覆盖契约、runtime、工具层、skill、orchestrator 等。

  workspace/
  本地任务样例和结果目录。真实任务一般包含：

  - agent_config.toml
  - context.json
  - project_code/
  - cr_result/

  完整审查流程
  当前完整 agentic 流程从 python -m cr_agent.smoke --config ... 进入，而不是 RUN.sh 默认路径。

  流程如下：

  1. bootstrap_runtime
      - 读取任务配置和上下文。
      - 确定 platform=gitlab|infcode。
      - 构建 ToolFacade。
      - 构建 context_runtime、dimension_runtime、summary_runtime。
      - 准备 result_dir。

  2. run_review
      - 启动 CRG background lifecycle。
      - 创建 ReviewState 和 MainAgentSession。
      - 调 build_skill_tools(session)，把三个 skill 包成主 agent 可调用工具：
          - collect_context
          - dimension_review
          - summarize_report

      - 构建 can_use_tool，用于限制 summarize 重试次数。
      - 调 agent_runtime.run_review_loop(...)。

  3. 主 agent loop
      - SdkMainAgentRuntime 把 skill tools 注册成 in-process MCP server。
      - Claude Agent SDK 的 query(...) 负责 agent loop。
      - 主 agent 根据系统提示调用 skill：
          1. 先 collect_context
          2. 再 dimension_review
          3. 再 summarize_report

      - summarize_report 返回 {valid, errors} 后，主 agent 决定是否再调用 summarize_report 修正报告。

  4. collect_context skill
      - 不是主 agent 直接调工具。
      - skill 内部调用 runtime_context.tool_facade.tools_for("context") 获取 context agent 工具。
      - 创建 context subagent 的 SDK options。
      - 调 context_runtime.query_subagent("context", prompt, tools)。
      - context subagent 在自己的模型调用里决定是否使用工具。
      - skill 解析输出，写 collected_context.json。

  5. dimension_review skill
      - 读取 config/dimensions.toml。
      - 按 platform 选择维度。
      - 用 asyncio.Semaphore 并发跑多个 dimension subagent。
      - 每个维度：
          - 读取 prompt/<dimension>.md
          - 调 tool_facade.tools_for("dimension")
          - 构造独立 prompt/options
          - 调 dimension_runtime.query_subagent("dimension", ...)
          - 写 dimensions/<dimension>.json

      - 所有维度结束后写 dimensions/manifest.json。
      - 单维失败不终止；全部维度失败才抛错。

  6. summarize_report skill
      - 接收 collected_context 和 dimension_scores。
      - 调 summary_runtime.query_subagent("summary", prompt, assembled_options=None)。
      - summary agent 默认无工具。
      - 解析 JSON 或降级包装 Markdown。
      - 然后内部立即调用 validate_json。

  7. validate_json
      - 纯 Python 校验。
      - 不走 agent。
      - 不拿工具。
      - 不维护 attempt。
      - 校验失败时，错误返回给主 agent，让主 agent 决定是否重调 summarize。

  8. run_review 收尾
      - 如果最后报告存在且 validation valid，则 status=success。
      - 否则 failed/error。
      - 写 result.json、cr_result.md、run.log。

  主 agent 什么时候调用 skill
  主 agent 在 run_review_loop 内调用 skill。Python 不再固定顺序直接调用 skill，而是把 skill 暴露成 SDK tool，交给主
  agent 根据系统提示规划调用。

  不过当前系统提示强约束顺序：

  collect_context -> dimension_review -> summarize_report

  所以它不是自由探索型 agent，而是受约束的阶段编排 agent。

  谁来调用工具
  分两层：

  - 主 agent 调用的是 skill tool，不直接调用底层工具。
  - context/dimension subagent 才可能调用底层工具。

  具体路径：

  skill
    -> runtime_context.tool_facade.tools_for("context" 或 "dimension")
    -> ToolFacade 根据 agent_tools.toml 过滤工具
    -> CrNativeToolProvider 或 InfcodeToolProvider 提供 ToolSpec
    -> SDK MCP server 暴露给 subagent
    -> subagent 决定调用哪些工具

  summary agent 不拿工具。

  validate_json 不拿工具。

  主 agent 什么时候做决策
  主 agent 当前主要有两个决策点：

  1. 阶段调用决策
      - 理论上由主 agent 决定什么时候调用 collect_context、dimension_review、summarize_report。
      - 但系统提示已经要求按固定顺序执行。

  2. summarize 重试决策
      - summarize_report tool 内部会调用 validate_json。
      - tool 返回 {valid, errors}。
      - 如果 valid=false，主 agent 可以决定再调用 summarize_report，把 validation errors 传入下一轮 summary
        prompt。

      - Python 的 can_use_tool 会做兜底限制：允许 summarize 调用次数是 max_retries + 1，超过就 deny。

  其它决策，例如维度数量、并发数、工具 allowlist，不由主 agent 决定，而是 Python 确定性代码决定。

  主 agent 会实现多轮对话吗
  会，但不是“用户聊天式多轮对话”。

  当前主 agent 使用 Claude Agent SDK query(...)，这是一个 agent loop：模型可以在一次审查任务里多轮调用工具、观察结
  果、继续调用下一个工具。

  所以它有 agent loop，但边界是单次 review run 内部。

  它不会和外部用户来回对话，也不会等待用户反馈后继续审查。

  有没有 agent loop
  有两个层面的 loop：

  1. 主 agent loop
      - 在 SdkMainAgentRuntime.run_review_loop 里由 Claude Agent SDK 的 query(...) 驱动。
      - 主 agent 可以多次 tool call。
      - 当前最重要的循环是 summary 校验失败后的重调。

  2. subagent tool loop
      - collect_context 和每个 dimension subagent 调用 query_subagent(...)。
      - 它们拿到自己的工具集后，也可以在模型调用过程中多次使用工具。
      - 例如 context subagent 可以 grep、read_file、crg_query，再归纳上下文。

  还有一个不是 agent loop 的 Python 并发 loop：

  - dimension_review 用 asyncio.gather + Semaphore 并发跑多个维度 subagent。
  - 这是确定性调度，不是主 agent 自主循环。

  当前实现和目标架构的差距
  最重要的差距是：

  - RUN.sh -> cr_agent.main 当前只 bootstrap，不跑完整审查；完整 agentic review 现在在 cr_agent.smoke。
  - SKILL.md 仍是占位。
  - 维度 prompt 输出格式和代码 JSON 解析契约还没统一。
  - summary prompt 没有真正接入 prompt/summary.md 和规则文件。
  - validate 还缺行号、diff 范围、line_comments/issues 对齐等强校验。
  - infcode provider 还是 stub。
  - 真实工具链和真实 LLM 端到端还需要继续联调。
