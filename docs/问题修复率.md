# Issue Resolution Agent Contract

本文档说明 codereviewbackend 与 cr-agent 在“行级评论问题完成状态判断”流程中的契约。

命令：
bash run_agent_resolution_check.sh \
  --config workspace/issue_resolution/22-96986a66/agent_config.toml \
  --platform gitlab

## 结论

这是一个新的 agent 契约，不复用原代码审查契约。

复用的部分是后端启动 agent 的通道：仍然通过 Docker 容器执行 cr-agent 仓库中的脚本，并通过 `agent_config.toml` 告诉 agent 输入文件和输出目录。

不复用的部分是输入输出 JSON：本流程不传 code diff，不传完整代码审查上下文，只传本次 MR 中仍处于 `open` 状态的行级评论问题，以及判断这些问题是否已经被解决所需的元信息。

## 触发时机

GitLab merge request webhook 进入 merge 分支后触发。

后端会先执行已有的 merged SHA 清理逻辑，然后在 `issue_resolution.enabled=true` 时执行本流程。当前默认配置为关闭：

```yaml
issue_resolution:
  enabled: false
  timeout_minutes: 20
  poll_interval_seconds: 5
```

如果配置关闭，后端不会启动 agent，也不会修改 `agent_line_reviews.state`。

## Agent 启动方式

后端流程如下：

1. 查询当前 MR 下 `state=open` 的 `agent_line_reviews`。
2. 生成任务目录，目录名为 `<mr_iid>-<merged_sha_prefix8>`，如果没有 merge SHA 则使用 `<mr_iid>-unknown`。
3. 写入输入文件 `issue_resolution_context.json`。
4. 写入 agent 配置文件 `agent_config.toml`。
5. 使用现有 Docker manager 创建或复用 agent 容器。
6. 检查容器处于 running 状态。
7. 在容器中执行：

```bash
bash /opt/cr-agent/run_agent_resolution_check.sh \
  --config /workspace/issue_resolution/<task>/agent_config.toml \
  --platform <agent.platform>
```

8. 后端轮询宿主机结果文件 `issue_resolution_result.json`。
9. 解析结果后，只更新本次输入中原本为 `open` 的行级评论。

这个流程是 post-merge 维护逻辑。agent 执行失败、结果超时或结果不合法时，后端只记录 warning，不影响 merge webhook 的返回。

## 文件路径

本流程和普通代码审查一样，通过配置中的宿主机 workspace 与容器内 `/workspace` bind mount 交换数据。

普通代码审查会在宿主机写入：

```text
<workspace_dir>/<task>/agent_config.toml
<workspace_dir>/<task>/context.json
<workspace_dir>/<task>/changes.diff
<workspace_dir>/cr_result/<task>/result.json
```

容器内对应：

```text
/workspace/<task>/agent_config.toml
/workspace/<task>/context.json
/workspace/<task>/changes.diff
/workspace/cr_result/<task>/result.json
```

issue-resolution 流程沿用同一个 workspace，只是把任务文件放在独立子目录，避免和普通审查任务混在一起。假设配置中的宿主机 workspace 为：

```text
<workspace_dir>
```

后端写入：

```text
<workspace_dir>/issue_resolution/<task>/issue_resolution_context.json
<workspace_dir>/issue_resolution/<task>/agent_config.toml
```

agent 需要写入：

```text
<workspace_dir>/issue_resolution_result/<task>/issue_resolution_result.json
```

容器内对应路径为：

```text
/workspace/issue_resolution/<task>/issue_resolution_context.json
/workspace/issue_resolution/<task>/agent_config.toml
/workspace/issue_resolution_result/<task>/issue_resolution_result.json
```

## agent_config.toml

后端写入的配置文件格式如下：

```toml
platform = "gitlab"

[context]
json_path = "/workspace/issue_resolution/<task>/issue_resolution_context.json"
result_path = "/workspace/issue_resolution_result/<task>"
```

`platform` 来自 `agent.platform`，为空时后端默认使用 `gitlab`。

cr-agent 侧应读取 `[context].json_path` 作为输入文件，并把结果写到 `[context].result_path/issue_resolution_result.json`。

## 输入文件

输入文件名：

```text
issue_resolution_context.json
```

Schema：

```json
{
  "task_id": "string",
  "project_id": 0,
  "mr_iid": 0,
  "mr_url": "string",
  "source_branch": "string",
  "target_branch": "string",
  "merged_commit_sha": "string",
  "issues": [
    {
      "line_review_id": 0,
      "discussion_id": "string",
      "note_id": 0,
      "file_path": "string",
      "line_number": 0,
      "severity": "string",
      "comment_body": "string",
      "head_sha": "string",
      "comment_url": "string"
    }
  ]
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `task_id` | 本次判断任务 ID。 |
| `project_id` | GitLab project ID。 |
| `mr_iid` | GitLab MR IID。 |
| `mr_url` | MR URL，可能为空。 |
| `source_branch` | MR source branch。 |
| `target_branch` | MR target branch。 |
| `merged_commit_sha` | merge webhook 中后端记录的 merge commit SHA。 |
| `issues` | 本次 MR 中仍处于 `open` 状态的行级评论问题。 |
| `issues[].line_review_id` | 后端数据库 `agent_line_reviews.id`，输出必须原样返回。 |
| `issues[].discussion_id` | GitLab discussion ID。 |
| `issues[].note_id` | GitLab note ID。 |
| `issues[].file_path` | 行级评论关联的文件路径。 |
| `issues[].line_number` | 行级评论关联的行号。 |
| `issues[].severity` | 问题严重级别。 |
| `issues[].comment_body` | 行级评论正文，也就是 agent 之前提出的问题描述。 |
| `issues[].head_sha` | 生成行级评论时关联的 head SHA。 |
| `issues[].comment_url` | GitLab comment URL，可能为空。 |

后端只会发送当前 `state=open` 的问题。已经被用户点踩 dismiss 的问题不会发给 agent。

## 输出文件

输出文件名：

```text
issue_resolution_result.json
```

Schema：

```json
{
  "task_id": "string",
  "status": "success",
  "results": [
    {
      "line_review_id": 0,
      "state": "solved",
      "reason": "string",
      "confidence": 0.95
    }
  ],
  "errors": []
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `task_id` | 建议返回输入中的 `task_id`。当前后端不强校验，但用于排查问题。 |
| `status` | 必须为 `success`，否则后端拒绝整份结果。 |
| `results` | 每个被判断问题的结果。可以少于输入问题数量。未返回的问题保持原状态。 |
| `results[].line_review_id` | 必须对应输入中的 `line_review_id`。未知 ID 会被后端忽略。 |
| `results[].state` | 只允许 `open` 或 `solved`。 |
| `results[].reason` | 状态判断原因，会写入 `agent_line_reviews.state_reason`。 |
| `results[].confidence` | 置信度，范围 `0` 到 `1`。缺省时后端按 `0` 处理，超出范围的 item 会被忽略。 |
| `errors` | agent 侧可选错误信息。`status=success` 时不会阻止后端处理合法结果。 |

重要约束：

- agent 不能返回 `dismissed`。`dismissed` 只由用户点踩触发。
- agent 判断问题未解决时返回 `open`。
- agent 判断问题已解决时返回 `solved`。
- 后端只更新本次输入中的 open 问题，避免旧任务或异常结果覆盖其他记录。

## 与原代码审查契约的区别

原代码审查流程使用完整审查上下文和结果文件，例如 `context.json`、`result.json`，其中包含 diff、项目路径、commit 信息、line comments、issues、token usage 等内容。

本流程使用独立的 `issue_resolution_context.json` 和 `issue_resolution_result.json`。输入只包含行级评论问题及 MR 元信息，输出只包含每个问题的完成状态判断。

因此 cr-agent 侧需要提供一个新的脚本 `run_agent_resolution_check.sh`，由后端单独调用。普通代码审查仍然使用原 `RUN.sh` 命令格式，本流程不再给 `RUN.sh` 增加新的 `--mode` 参数。

## cr-agent 端需要支持的改动

cr-agent 侧需要增加一个独立脚本 `run_agent_resolution_check.sh`。后端不会修改或复用原代码审查的输入输出 schema，因此 agent 侧不要把本流程当作普通 code review 任务处理。

最小改动要求如下：

1. 在 cr-agent 仓库根目录提供 `run_agent_resolution_check.sh`，容器内默认路径为 `/opt/cr-agent/run_agent_resolution_check.sh`。
2. 该脚本接收 `--config` 和 `--platform` 参数，不需要支持 `--mode`。
3. 脚本读取 `--config` 指向的 `agent_config.toml`。
4. 从 `agent_config.toml` 的 `[context]` 中读取：

```toml
json_path = "/workspace/issue_resolution/<task>/issue_resolution_context.json"
result_path = "/workspace/issue_resolution_result/<task>"
```

5. 反序列化 `json_path` 指向的 `issue_resolution_context.json`。
6. 对 `issues` 中的每个问题判断状态：
   - 问题仍未解决时返回 `open`。
   - 问题已经解决时返回 `solved`。
   - 不要返回 `dismissed`，该状态只由用户点踩产生。
7. 为每个返回项填写：
   - `line_review_id`：必须使用输入中的原始 ID。
   - `state`：只能是 `open` 或 `solved`。
   - `reason`：说明判断依据。
   - `confidence`：`0` 到 `1` 的置信度。
8. 将结果写入：

```text
<result_path>/issue_resolution_result.json
```

也就是容器内路径：

```text
/workspace/issue_resolution_result/<task>/issue_resolution_result.json
```

推荐 agent 侧成功输出：

```json
{
  "task_id": "input-task-id",
  "status": "success",
  "results": [
    {
      "line_review_id": 123,
      "state": "solved",
      "reason": "The merged code now validates nil input before dereferencing it.",
      "confidence": 0.87
    },
    {
      "line_review_id": 124,
      "state": "open",
      "reason": "The merged code still writes to the shared map without synchronization.",
      "confidence": 0.76
    }
  ],
  "errors": []
}
```

如果 agent 侧遇到不可恢复错误，可以写出：

```json
{
  "task_id": "input-task-id",
  "status": "failed",
  "results": [],
  "errors": ["failed to inspect merged code"]
}
```

后端收到非 `success` 状态时会拒绝整份结果，并保持数据库状态不变。

### agent 判断所需上下文

后端不会在该契约中传入 code diff。agent 如果需要查看合并后的代码，应基于输入中的 `project_id`、`mr_iid`、`merged_commit_sha`、`file_path`、`line_number` 等信息，通过 agent 自己已有的平台能力获取代码或 MR 信息。

后端传给 agent 的行级评论正文是 `comment_body`。它是需要判断是否解决的问题描述，agent 应把它作为主要问题文本使用。

### agent 侧兼容性要求

- `results` 可以少于输入的 `issues`。未返回的问题在后端保持 `open`。
- `results` 中出现未知 `line_review_id` 时，后端会忽略该条。
- `confidence` 缺省时后端按 `0` 处理；超出 `0` 到 `1` 范围时，该条结果会被忽略。
- `state` 返回除 `open`、`solved` 以外的值时，该条结果会被忽略。
- `status` 不是 `success` 时，后端拒绝整份结果。
