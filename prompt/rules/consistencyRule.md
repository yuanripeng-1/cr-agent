# 一致性维度评分规则

## 单条问题评分（score: 0-100）


**初次判定危险严重度分档（单条问题同时符合多个档位时，取最高档为基准分）**
- **85–100:**引入与代码库契约冲突的范式,破坏既有调用方。
- **65–84:** 违反已确立的架构模式(绕过既有分层/仓储直连 DB——若同时破坏既有调用方则升至 85-100);API 契约不一致(同类接口返回结构迥异);混用多套约定造成系统性混乱。
- **40–64:** 命名约定与全局不符;错误/日志范式与其余代码不同;同类函数返回类型不一致;违背项目既定的语言惯用风格。
- **20–39:** 局部风格偏差;格式与周围代码不一致。
- **1–19:** import 排序、引号风格等琐碎差异。
- **0:** 与代码库约定一致,未发现问题。


**加减分策略**
先基于"**初次判定危险严重度分档**"确定档位，取该档位中间值作为基准分，然后再按下列因素调整:单因素 ±5~15,同向可累积,但单次调整最多 ±20（含跨档）；调整后 clamp 到 `[0,100]` 并记录命中因素。
- 加分项（每项 +5~+15，影响越直接越高）：
  - 违反项目强约定（命名、结构、模式）并影响协作一致性
  - Linter 报错或规则违背可直接确认
  - 公共接口命名/语义不一致，导致误用风险
  - 同类代码实现风格明显分叉
  - 同一逻辑端点的多个方法变体/入口采用不同的注册或声明机制（不同源），后续修改易产生漂移——属结构/模式约定不一致，非纯风格分叉
- 减分项（每项 -5~-15，影响越不确定越低）：
  - 仅个人风格偏好，未违反项目约定
  - 无规则依据或无 Linter 证据
  - 影响面不清晰
